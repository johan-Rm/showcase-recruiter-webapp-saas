# showcase-recruiter-webapp-saas — Internationalisation (i18n)

> Deux couches : UI (webapp Nuxt) et données (entités traduisibles côté Symfony). Complète
> [architecture.md](./architecture.md).
>
> Langues : **FR** (locale source / fallback), **AR** (arabe, **RTL**), **EN**.

## Deux couches distinctes

| Couche | Périmètre | Mécanisme |
| --- | --- | --- |
| **UI** | tous les libellés d'interface | `@nuxtjs/i18n` + fichiers de locales (webapp) |
| **Données** | référentiels + contenu éditorial | entités traduisibles (modèle Sylius-style, `api/`) |

## Couche UI — webapp Nuxt (`@nuxtjs/i18n`)

- Module `@nuxtjs/i18n`, locales **FR / AR / EN**, `defaultLocale` = FR (fallback).
- **`dir` par locale** : `FR`/`EN` = `ltr`, **`AR` = `rtl`** (déclaré dans la config des locales).
- Le catalogue de langues dérive d'un **registre partagé** (`shared/`) — aucune liste de langues
  en dur dans la config Nuxt.
- Détection de la langue navigateur (cookie `showcase-recruiter-webapp-saas_locale`).
- Fichiers de locales dans `base/i18n/locales/` (`fr.yaml`, `ar.yaml`, `en.yaml`).
- **Tout texte visible passe par une clé de traduction** — jamais de chaîne en dur.
- SSR-safe : la résolution de locale doit fonctionner côté serveur (hydratation cohérente).

### La parité des trois fichiers est vérifiée

Le repli sur le français rend une traduction manquante **invisible** : la clé absente n'affiche pas
un fragment technique, elle affiche le texte français. L'écran reste lisible, rien ne signale
l'anomalie — sauf à un lecteur anglophone qui trouve une phrase française au milieu de sa page, ou à
un lecteur arabophone dont l'interface change de langue *et de sens de lecture* en cours de route.

Un test (`base/i18n/locales/parity.vitest.ts`) refuse donc quatre dérives, et **nomme** les clés
fautives plutôt que de les compter :

| Ce qu'il refuse | Ce que ça produirait sans lui |
| --- | --- |
| Une clé française sans équivalent ailleurs | du français au milieu d'un écran anglais ou arabe |
| Une clé qui survit dans une langue et plus en français | une couverture apparente qui n'existe plus |
| Un paramètre nommé perdu à la traduction (`{count}`, `{name}`) | une phrase amputée, sans erreur |
| Un nombre de formes plurielles différent du français | un pluriel qui se casse en silence |

Le test lit les fichiers **sans démarrer l'application**, et tire la liste des langues du registre
partagé : une langue ajoutée là est couverte ici sans rien toucher. Il compare l'**ensemble** des
paramètres et non leur nombre d'occurrences — une branche de pluriel peut légitimement écrire le
nombre en toutes lettres, comme l'arabe qui dit « un seul fichier » plutôt que « 1 fichier ».

Ce n'est pas une règle bloquante à la fusion : celles-ci vivent dans le socle et gouvernent tout le
dépôt. Le test suffit, il tourne avec les autres, et il échoue le jour où quelqu'un oublie une
langue.

## RTL — arabe (impact UI fort)

L'arabe est **droite-à-gauche** : ce n'est pas qu'une traduction, c'est un **layout miroir**. À
intégrer **dès le design** (cf. [4.design/brand-guidelines.md](../4.design/brand-guidelines.md)) :

- `dir="rtl"` piloté par la locale active (`@nuxtjs/i18n` expose la direction).
- **CSS en propriétés logiques** : `margin-inline`, `padding-inline`, `inset-inline`, `text-align: start/end` — **jamais** `left/right` en dur.
- Composants **miroir** : navigation, icônes directionnelles, ordre des colonnes, sliders.
- Tester chaque écran en `rtl` (l'AR n'est pas un simple remplacement de texte).
- Tailwind : activer le support RTL (plugin / variantes logiques).

## Couche données — modèle traduisible Symfony (Sylius-style)

Pattern : entité **racine** + entités **`*Translation`** séparées.

- La **racine** garde identité, statut, relations non localisées, champs d'audit.
- Chaque **`*Translation`** garde les champs éditoriaux localisés, `locale`, et le lien vers la
  racine. Contrainte d'unicité **`(resource_id, locale)`**.
- **Résolution de locale** : lecture via `?locale=fr` ou `Accept-Language` ; si la traduction
  demandée manque, **fallback sur la locale source** (FR), et la réponse expose
  `requestedLocale`, `locale`, `fallbackLocale`, `fallback`.
- Les lectures standard exposent les champs localisés **directement sur la racine** et masquent
  la collection technique `translations`.
- **Écriture** (PUT/POST) : pas de fallback — la locale ciblée est utilisée telle quelle, créant
  la traduction si elle n'existe pas.

## Ce qui est traduisible

| Donnée | Traduisible ? | Pattern |
| --- | --- | --- |
| **Secteur / fonction / compétences** | non | **valeurs libres** portées par la donnée (référentiel `CategoryCode` abandonné le 2026-07-13) |
| **Éditorial** (cartes « profils stars », contenu landing) | oui | racine + `*Translation` |
| **Profil candidat** (CV, expériences, accroche) | non | **mono-langue** (langue d'origine du candidat) |
| Libellés d'options / packs crédits | oui (éditorial) | racine + `*Translation` |

Le profil candidat **reste dans sa langue d'origine** : le CV et les expériences ne sont pas
traduits. Seul le **contenu éditorial** est stocké en multi-langues ; les libellés d'interface vivent
dans le catalogue i18n du front.

## Dark mode

Thème clair / sombre purement **webapp** (Tailwind / `@nuxtjs/color-mode`) — **aucun impact sur le
modèle de données**, aucune incidence sur l'`api/`.

## Implications pour le modèle de données

- Les entités **référentiels** et **éditorial** suivent le pattern racine + `*Translation`
  (`(resource_id, locale)` unique).
- Les champs du `Candidate` sont **plats** (non traduisibles) — sa langue d'origine est une simple
  métadonnée (`originLocale`).
- Les **locales activées** et la **locale source** (FR) sont configurées au niveau projet/app.
